# 操作文件文字規範

規範識別：writing-pilot-20261013.2。完整版與輕量版採用相同文字規範；各版取證、隱碼、版面與驗證流程仍依自己的 skill。首次撰寫或修訂操作文字前閱讀本文件。適用於功能介紹、步驟、欄位表、結果、圖說與提醒，不要求改寫畫面原文或不在本次範圍的內容。

正文面向一般系統操作者。正文保留完成操作所需的操作、條件、選項與計算影響；先用畫面名稱與日常用語說明結果及適用情況，必要的業務詞在首次出現時簡短解釋，UI 原文照保留。代理或起草者的試作操作、未儲存／未執行狀態、工具名稱、雜湊、人工 pending 與 QA 限制放在 QA record、finding ledger、review artifact 或交付說明。產物仍為 draft 時，以檔名或交付說明標示；只有既有章節確實需要，而且有證據且對讀者有用時，才在正文留下提醒。不得把「本次不要儲存」等試作限制改寫成業務操作規則。

- 文件面向一般使用者。
- 盡量避免過多數學或電腦專用用語；必要的畫面原文與業務詞保留並簡短說明。
- 說明文字需要清晰、直白，讓讀者知道要做什麼及選項會造成什麼影響。

## 寫作依據與語氣

使用中性、直接、可執行的繁體中文。以既有 scopeMatrix／fieldInventory 與來源證據起草；術語對照及未確認事項沿用同一 QA record，不另建一套證據清單。

- 控制項名稱逐字對應畫面，以「」標示。相同概念使用相同名稱，不為避免重複而把「儲存」改成「提交」。不同畫面本來名稱不同時保留原名，必要時說明對應關係。
- 優先用「在……輸入……」「選擇……」「按……」描述動作；一個步驟以一個主要動作為原則。遇到等待、確認或條件分支時拆開；同一位置的簡短連續動作可以合併，不訂固定句長或步驟數。
- 刪除不增加操作資訊的開場、結語、宣傳語與客套話，例如「有效提升效率」「接下來將詳細介紹」「希望本說明對您有所幫助」。保留影響操作的警告與因果說明。
- 明確區分讀者操作與系統反應。主體不清時補明主體；不要求每句重複「使用者」，也不禁止語意清楚的被動句。
- 保留業務術語、錯誤訊息、UI 原文、數值、否定及適用條件。引號、編號、表格與適量強調用於辨識，不作機械刪除或全面禁用。
- 具體資訊只能來自證據或使用者。不得補造必填、格式、長度、預設值、權限、處理時間或下游影響。畫面成功提示只證明已觀察到該提示；資料回查與下游結果需有各自證據。
- 未確認的必要資訊依既有規範記為待確認並回到取證；不以推測補滿段落。可省略不影響操作、也不屬必要範圍的空泛句子，不得藉精簡刪除必要流程。

可驗證的 repository／tag／release 資訊可依既有版型在正文的版本依據簡述一次；來源分類、程式識別字、方法追蹤、capture state、雜湊與其他取證細節留在 QA。沒有可驗證來源時省略版本推論。正文與 QA 使用的名稱要能互相回指，但不要把 QA 追蹤欄位當成讀者步驟。

## 各類文字的工作

| 內容 | 應交代的資訊 |
| --- | --- |
| 功能介紹 | 系統操作者可完成什麼工作，何時使用。通常一至兩句即可，無需宣傳效益。 |
| 前置條件 | 已確認的資料狀態、先行操作與具體角色或權限；權限若無角色證據就寫待確認或省略。 |
| 步驟 | 操作位置、畫面控制項名稱與動作；適用條件先寫，分支各自指明去向。 |
| 欄位與選項表 | 填什麼或顯示什麼、值來源、必填與限制；計算選項另交代適用條件、改變的結果、順序及未命中／未填的退回規則。 |
| 成功結果與檢核 | 可觀察的變化及如何回查；只有觀察到提示時不得宣稱資料或下游作業均完成。 |
| 圖說 | 畫面狀態、紅框目標或本圖差異，編號對應當張圖；不複製完整步驟。隱碼敘述與實際範圍一致。 |
| 失敗、取消與警告 | 已確認的觸發條件、畫面反應、資料影響與可採取的動作。沒有證據時不得自行建議重送或重試。 |

這是內容提示，不要求每段湊滿所有項目。共通流程集中說明一次，各章保留適用條件、差異及明確交叉引用。刪除重複前確認讀者仍能找到完成任務所需資訊。

## 抽象措辭回查

「完整」「正確」「符合規範」等詞不是禁用詞，也沒有硬性字數限制；回查時要問讀者能否依這句話完成判斷。若保留這類詞，需同時列出具體欄位與判斷，或精準引用能讓讀者找到判斷依據的章節、表格、訊息或規則。

- 「具備權限者」只有在證據證明具體角色、角色可執行的動作或畫面可觀察的權限差異時才可寫；沒有證據就不添加這項限制。
- 「依情況」「依相關設定」要改成情況與處理的對應，例如不同選項、狀態或資料條件各自說明下一步；不能把不明確的設定名稱留給讀者猜。
- 只有語氣偏好或純冗詞而不影響操作時，才按非阻擋 finding 處理；若含糊使讀者無法操作、判斷或回查，依阻擋規則處理。

## 計算選項與算例

對會改變金額、數量、日期或其他計算結果的每個 UI／業務選項，讓讀者在同一節找得到以下資訊：

1. 什麼條件下適用，包含必要的資料狀態或選項組合。
2. 選取後改變什麼結果或資料。
3. 多個條件或步驟的計算順序。
4. 未命中條件或未填值時的退回、預設或提示規則。

正文使用畫面上的 UI 名稱與業務名稱；內部變數、方法名稱與程式識別字留在 QA 證據。若來源沒有證明適用條件、順序或退回規則，寫待確認並回到取證，不為了讓說明看似具體而補造事實。

算例只有在能幫助讀者依規則理解選項時才加入。先用白話說明順序；必要時才用簡單數字例子，列出假設、輸入、公式或計算方式、順序與結果，並標示「合成示例，非實測」。避免大量公式符號、英文變數與程式術語，不得因此遺失條件或改變公式。不得把合成結果寫成系統實測，也不得加入來源未支持的業務規則／結果。無法證明公式或假設時省略算例。

## 寫法示例

以下案例都是泛用合成案例，不是任何實際系統的事實；只有來源支持時才採用其中的控制項與行為。合成案例只用來說明寫法，不是實測結果。

| 原句或情境 | 建議處理 |
| --- | --- |
| 「透過查詢功能，可快速有效地掌握相關資訊。」 | 若證據有「帳單號碼」與「查詢」：寫「在『帳單號碼』輸入查詢值，按『查詢』。」正式文件使用「」標示控制項。 |
| 「帳單號碼：用於輸入帳單號碼。」 | 已確認為查詢欄位時，寫「輸入要查詢的帳單號碼。」不另加未確認的字數或完整比對規則。 |
| 「按儲存後，所有後續作業將自動完成。」 | 若只觀察到「儲存成功」，寫「畫面顯示『儲存成功』。」不得補寫排程、通知或帳務更新。 |
| 「未送審且未鎖定時才能修改。」 | 保留兩個條件及「且」的關係；不能縮成「未送審時可修改」。 |
| 「依相關設定計算。」 | 若證據能區分選項，改寫為各選項的適用條件、影響、順序及未命中／未填處理；若不能區分，標為待確認，不猜設定內容。 |
| 「計算結果正確。」 | 列出讀者可看到的輸入、計算選項、公式或順序，以及可回查的結果欄位；沒有這些證據時不宣稱正確。 |
| 「具備權限者可修改。」 | 只有證據指出具體角色及其可用控制項時才寫角色與限制；否則刪除未證實的權限限制。 |
| 「本次試作不儲存資料。」 | 若只是取證或 QA 限制，移至 QA／交付說明；只有觀察到系統取消或未儲存行為且對操作者有用時，才描述該業務行為。 |
| 「取消後不會儲存本次變更。」且來源已確認 | 保留否定及「本次」範圍，不能改成「取消後刪除資料」。 |
| 圖說寫「識別資訊與金額均已隱碼」，實際只遮識別資訊 | 改成與實際遮蔽範圍相符的圖說；不為配合原句而擴大隱碼範圍。 |
| 「假設基準金額為 100、比例為 20%，結果為 20。」 | 若確有必要，先用白話說明計算順序，再標示為「合成示例，非實測」，列出假設與必要公式；不能把這個數值當成來源未支持的業務規則／結果。 |

## 起草、整理與回查

先由證據起草，再整理文字，最後對照來源回查。檢查的是語意與可操作性，不是特定句型、「像不像 AI」、固定字數或禁用詞清單。

1. 一般操作者能否用畫面名稱與日常用語知道去哪裡、按什麼、填什麼？必要業務詞是否在首次出現時簡短解釋，UI 原文是否保留？位置、名稱與圖中目標是否一致？
2. 抽象詞是否有具體欄位、判斷或精準引用；權限是否有具體角色證據；「依情況／相關設定」是否列出情況與處理對應？
3. 每個計算選項是否說明適用條件、改變什麼、計算順序及未命中／未填退回規則？順序是否先用白話，算例是否有必要、假設清楚且依公式？是否避免大量公式符號、英文變數與程式術語而不遺失條件？
4. 條件、順序、否定、權限與數值是否在改寫後完整保留？分支是否仍可跟隨？
5. 結果、限制與警告是否各有依據？是否把提示誤寫成已確認的資料或下游結果？
6. 刪掉的句子是否真的不影響完成操作？是否留下指向不存在章節或圖號的引用？
7. 真正輸出的 DOCX 中，正文、步驟、表格與圖說是否仍一致？不能只查改寫來源。

起草後的編輯回查只把實際問題記入既有 finding ledger：保留原句、問題、修正內容或保留理由，以及可回查的 evidence。不要為每一句建立紀錄，不新增 schema 欄位或 review 輪次。改寫後重新檢查條件、順序、否定與數值，建置後讀回真正 DOCX 的正文、表格與圖說，確認改寫已進入成品。

錯誤控制項、含糊到無法操作、未證實的權限限制、計算順序錯誤、遺漏必要條件、或未證實且影響操作的結果或限制屬阻擋項，不能以文字潤飾結案。純冗詞、句型偏好、一般語氣改善或不影響主要流程的措辭精緻度屬非阻擋項，按現行 accepted limitation 規則處理，不為偏好反覆重建。

沿用既有獨立 reviewer 機制，由未參與產製的 reviewer 執行；builder、腳本與機械報告可以提供 evidence，不能取代 reviewer 判讀或宣稱 reviewer 已通過。若本任務指定人工 reviewer，人工確認前保留 pending，並在外部 QA／交付說明標示；不要把 pending 寫入正文當成業務規則。reviewer 在現有 requirements／operation checks 中核對上述項目，沿用 reason／evidence 及輸出 hash，不增設必填 schema 或額外 review 輪次。

完整版按原流程檢查改寫後的實際渲染。輕量版讀回 DOCX 正文、表格、圖說及結構，不把內容預覽當成 Word 換行或分頁已驗證。兩版文字品質標準相同。
